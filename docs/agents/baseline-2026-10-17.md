## Confirmed issues and order of work

### 1. Share request handling and make request admission explicit

The actual voice worker sends no tools to inference; the text API offers tools and
has a separate execution loop. The deterministic handler probe sends the same
command through both paths with fake inference and records that difference. This
is a wiring defect regardless of whether the eventual interpreter uses structured
JSON or bounded tool calls. Current disabled-control conversation cases cannot
establish real control success.

The queue probe submits two requests from different sessions to the one-slot queue
and demonstrates displacement of the first pending request. This is reproducible
without CPU overload or a model error. There is no caller-visible admission result.

First change: one request service for voice/text, request/session IDs, explicit
accepted/busy/cancelled/expired outcomes, and bounded inference admission. Keep the
execution boundary behind a fake provider initially. Test identical bilingual
requests, interleaved sessions, and overload; no accepted request may disappear
silently. Do not resolve this by making the queue unbounded on a four-core server.

Evidence: [process_text](../../app/main.py), `_llm_worker`, `_enqueue_final_llm`,
and [diagnostic probe](../../scripts/e2e/diagnose_server.py).

### 2. Repair bilingual turn and response behavior

- Narratives in both languages are truncated at exactly 80 generated tokens, through
  both text and voice. The provider reports `done_reason=length`; the application
  adapter discards that metadata and treats the partial content as a completed reply.
  The deployed 48-token limit deserves the same test; this run did not measure it.
- A French numeric text answer uses the English voice; a later English numeric
  voice answer uses the French voice. `_run_speak` reuses a shared `_last_lang` for
  short text. The output string `4` cannot determine the user's language.
- French two-sentence input can split into two requests, producing an unwanted
  response to the instruction to answer briefly. Address the client endpointing /
  server turn-boundary contract; do not label this solely an ASR model failure.

Carry input/session language into TTS, handle model stop reasons, and define short
complete reply budgets. Use deterministic short confirmations for known outcomes;
benchmark modest generation-cap changes for narrative conversation separately.
Do not simply increase every request to 1024 tokens. Preserve the raw failing
fixtures as regressions and include negation, pauses, and French number words.

Evidence: `Baseline.Model`, `ARIA.TTS.Language`, and transcript events in the run;
[LLM adapter](../../app/llm/ollama_client.py), [speech output](../../app/speech_output/speech_output.py).

### 3. Establish truthful, validated control outcomes before live actions

`ActionsProvider.execute_command` calls publish return-code success `success=True`.
Its message correctly says published; this does not establish observed device
completion. Keep accepted/published/observed/failed states distinct through the
response layer. Require grounded device IDs, valid payloads and an application
execution trace; never count tool calls as proof of the intended action.

The unavailable-control baseline responses disclaim capability and make no observed
completion claim. That is expected with actions disabled and an explicit no-control
system prompt. It says nothing about the real tool loop's accuracy. Next evaluate
that loop against a fixed fake inventory/executor, including ambiguity, negation,
unsupported requests, duplicate delivery, and provider timeouts.

Evidence: [actions provider](../../app/plugins/actions/provider.py), historical
[findings](status.md). No live MQTT commands were sent in this baseline.

### 4. Repair optional paths, then compare architecture candidates on Apollo

A forced-CHAT diagnostic exercises the actual text handler: an English factual
question receives the generic French greeting and `spoken=False` even when speech
was requested. This proves a branch-handling defect; the classifier itself was
stubbed, so it is not a measurement of current router accuracy. Keep the router out
of the acceptance profile until generic conversation reaches the response pipeline
and both entry points honor the same speech contract.

After the shared path works, compare the current tool loop, bounded tool proposals,
and constrained interpretation using the same small local model and held-out
bilingual control cases. Measure routing on/off separately. Nothing in this run
justifies buying hardware, loading a 7B model by default, adding more services, or
committing to Option A. Resource contention, power, and full-feature offline behavior
remain separate measurements. The [architecture review](architecture-options.md)
is a proposal, not an accepted decision.

## Coverage limits

The corpus has four prompt pairs: arithmetic, capital of France, short cat story,
and a living-room light command with control unavailable. Each runs once as text
and once as audio. The factual pair also runs through the real microphone. Model
temperature is zero, but this is one run with cached repeats, not an independence
or statistical reliability claim. Report small-sample p95 only descriptively.

Exact-answer checks cover arithmetic and the presence of Paris. They do not catch
extra replies or establish narrative quality; those were reviewed from raw outputs.
Normalized word error rates ignore punctuation/case/accents but retain number-word
versus digit differences. They compare the input prompt to transcripts forwarded to
the LLM, not an independently recorded ASR output before filtering/queueing. Do not
present them as isolated ASR-model accuracy or intent error rates.

Full speech-end-to-audible-output latency, physical speaker quality, sustained load,
ASR stage timing, power consumption, acoustic echo/barge-in, real device completion,
model downloads at startup, and production offline operation with LAN providers
are not certified by this run. HTTP audio retrieval is the measured output boundary.
